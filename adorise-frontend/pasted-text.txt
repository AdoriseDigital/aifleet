  # InboxCalm — Auth & Routing Fix Spec

  **For:** Mika (implementation in Multica)
  **Source:** Launch-readiness audit, 2026-09-16 (`Claude/Output/APP-LAUNCH-READINESS-AUDIT.md`)
  **Goal:** Make `inboxcalm.adorisedigital.com` a real, logged-in product instead of a static marketing page with an
  external checkout link.

  ---

  ## Problem (confirmed live, 2026-09-16)

  - `/login`, `/signin`, `/auth`, `/app`, `/dashboard`, `/signup`, `/register` all return HTTP 200 but serve
  byte-identical HTML to the homepage — no server-side routing exists at all.
  - There is no `<form>`, no `type="password"`/`type="email"` input anywhere on the site.
  - All CTAs ("Try 7 Days Free," "Get Pro Protection") link directly to `https://whop.com/adorise-digital-usa/` — Whop
  handles checkout, but nothing hands the user back into a real account or dashboard afterward.
  - Net effect: a paying customer has nowhere to actually log in and use the product.

  ## What already exists to build on

  Per the business's own infra docs (`Claude/Wiki/vps-infrastructure.md`, `agent-fleet-and-approval-gates.md`):
  - Self-hosted **Composio API** (FastAPI) already handles OAuth for other apps — reuse this rather than building a new
  OAuth stack.
  - **Postgres 16** + **Redis 7.2** already running on the shared VPS, isolated per-app via Docker networks.
  - **Whop** is already the monetization/entitlement system site-wide — don't replace it, wire it in properly.
  - All 6 apps sit behind **Caddy + Cloudflare**, so TLS/routing infra is already in place; this is purely an app-layer
  gap.

  ## Required changes

  ### 1. Real routing
  Replace the current "everything 200s to the homepage" behavior with actual routes:
  - `/login`, `/signup` → dedicated pages with real email/password form (or OAuth via Composio) — not a JS modal on the
  homepage.
  - `/app`, `/dashboard` → must **require an active session**; unauthenticated visitors get redirected to `/login`, not
  served the dashboard or the homepage.
  - Any route with no real implementation yet should return a proper 404, not a silent copy of the homepage — a 200 on a
  dead route is worse than an honest 404.

  ### 2. Real authentication
  - Email/password signup with hashed passwords (bcrypt/argon2) stored in Postgres, **or** OAuth (Google) via the
  existing Composio integration — pick whichever the other apps already standardized on, for consistency.
  - Server-side session (signed cookie or JWT), not `localStorage` — a purely client-side "login" (as seen on
  Scout/DearMee) is not real auth and shouldn't be the pattern copied here.
  - No fake/mock login paths — every login attempt must hit a real backend check.

  ### 3. Whop entitlement sync
  InboxCalm's pricing is Free (5 scans/day) / Pro $19/mo / Business $49/mo. The dashboard needs to know which tier a
  logged-in user is on:
  - Listen for Whop webhook events (subscription created/renewed/cancelled) and store the resulting plan tier against
  the user's account in Postgres.
  - Gate scan volume server-side against that stored tier (not client-side), so the daily/monthly limits are actually
  enforced.
  - On first login after a Whop purchase, match the account by email to link the Whop membership to the InboxCalm
  account.

  ### 4. Data model (minimum viable)
  - `users`: id, email, password_hash (nullable if OAuth-only), created_at
  - `subscriptions`: user_id, whop_membership_id, plan_tier, status, renewed_at
  - `scans`: id, user_id, input_email_text, toxicity_score, suggested_reply, created_at — this also gives you scan
  history in the dashboard, which the current site doesn't offer at all.

  ### 5. Don't touch (already working)
  - Landing page copy, demo widget, and pricing display — the audit rated these the best of all 6 apps. No changes
  needed there.
  - Whop as the checkout/payment processor — keep it, just close the loop after checkout instead of leaving the user
  stranded on an external page.

  ---

  ## Acceptance criteria (how I'll re-verify once deployed)

  1. `curl` diff of `/login`, `/dashboard`, `/` — must no longer be byte-identical.
  2. `/dashboard` without a valid session must redirect to `/login`, not 200 with dashboard content or homepage content.
  3. A real `<form>` with password input must be present on `/login`.
  4. No `alert()`/`localStorage`-only auth logic in the page JS.
  5. Grep for `fetch(`/`/api/` calls confirming the login form actually talks to a backend.

  Ping me once it's deployed and I'll re-audit this one app the same way we did the first pass.
